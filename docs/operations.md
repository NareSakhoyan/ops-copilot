# Operations

Single-host Docker Compose deployment of `ops-copilot`: `postgres`, a one-shot `migrate`,
`api`, and `jaeger`. See [README.md](../README.md#run-in-containers) for a quick start and
[security.md](security.md) for the security controls referenced below.

## First-time setup

```sh
cp .env.example .env            # host-side defaults only; containers get config from below
./scripts/generate-secrets.sh   # writes secrets/*.txt (gitignored) -- postgres/jwt/pepper, plus
                                 # a PLACEHOLDER secrets/database_url.txt
docker compose up -d --wait postgres migrate
```

`migrate` applies Drizzle migrations and the derived analytics grants as `migration_owner`, then
exits; `docker compose up --wait` only waits on services with a healthcheck, so check its exit
code separately if scripting this (`docker compose up migrate` in the foreground propagates it).

App access uses a separate `app_user` login whose password is deliberately never generated by
bootstrap SQL or this script (see [security.md](security.md#local-login-setup)). Set it
interactively, then replace the placeholder:

```sh
docker compose exec postgres psql -U migration_owner -d "$POSTGRES_DB" -c "\password app_user"
printf 'postgresql://app_user:<the password you just set>@postgres:5432/%s' "$POSTGRES_DB" \
  > secrets/database_url.txt
docker compose up -d --wait api
```

Optionally seed demo data (refuses to run with `NODE_ENV=production`; see
[seed-scenarios.md](seed-scenarios.md)):

```sh
NODE_ENV=test docker compose run --rm seed
```

## Start / stop

```sh
docker compose up -d --wait        # start everything (api waits on migrate + postgres health)
docker compose ps                  # status
docker compose logs -f api         # tail one service
docker compose down                # stop, keep the postgres_data volume
docker compose down -v             # stop and delete all data -- destructive
```

`api` and `postgres` have `restart: unless-stopped`; `migrate`/`seed` are one-shot
(`restart: "no"`) by design. `jaeger` also restarts `unless-stopped` but has no `healthcheck:`
(its official image ships no shell/curl/wget to run a probe with; see docs/security.md).

## Migrations

Generate a migration after changing the Drizzle schema (`npm run db:generate`, on the host, with
devDependencies), commit the generated SQL under `drizzle/`, then redeploy: `migrate` reruns
automatically as part of `docker compose up` because `api` depends on
`migrate: condition: service_completed_successfully`. There is no automatic rollback; forward-only
migrations are the supported path (see [decisions.md](decisions.md) "Initial migration
lifecycle").

## Secret rotation

Every secret is read from `VAR` or `VAR_FILE` (`src/secrets.ts`); Docker Compose mounts the
`secrets:` files at `/run/secrets/*` and `_FILE` wins when both forms are set. To rotate one:

1. Write the new value to the corresponding `secrets/*.txt` file.
2. `docker compose up -d --build api migrate` (or just `api` if only app-facing secrets changed)
   to recreate the affected containers with the new value.

Effects of rotating each secret:

| Secret | Effect of rotation |
| --- | --- |
| `jwt_secret.txt` | Invalidates every outstanding access token immediately; users must log in again. |
| `refresh_token_pepper.txt` | Invalidates every outstanding refresh token (stored hashes no longer match); access tokens already issued remain valid until they expire (<=15 min). |
| `postgres_password.txt` | Only takes effect on a fresh `postgres` data volume (the official image sets the superuser password at first init only); on an existing volume, change it with `ALTER ROLE migration_owner WITH PASSWORD ...` instead and update the file to match. |
| `database_url.txt` / `migration_database_url.txt` | Update together with the matching Postgres role's actual password (`ALTER ROLE ... WITH PASSWORD ...`), then restart the affected service(s). |

`GOOGLE_APPLICATION_CREDENTIALS` (Vertex) is not part of this app's secret loader by design (see
[decisions.md](decisions.md) "Add Vertex AI as a chat model provider"): point it at a mounted
secret file's path directly, e.g. add a `vertex_sa_json` entry to compose's `secrets:` block and
set `GOOGLE_APPLICATION_CREDENTIALS: /run/secrets/vertex_sa_json` on `api`.

## Backups

Not implemented by this change. `postgres_data` is a named Docker volume; a minimal approach for
a single host is a periodic `docker compose exec postgres pg_dump -U migration_owner "$POSTGRES_DB"`
piped to a file stored outside the volume, but scheduling, retention, and restore verification
are intentionally out of scope here.

## Known limits (single-host deployment)

- **Single instance**: one `api` container, one `postgres` container. No load balancing,
  read replicas, or automatic failover.
- **In-memory rate limits**: `@fastify/rate-limit`'s default store is per-process memory (see
  [security.md](security.md#rate-limiting)). It resets on restart and does not coordinate across
  multiple `api` replicas -- fine for one instance, not for horizontal scaling without first
  switching to a shared store (e.g. Redis).
- **No reverse proxy / TLS termination**: `api`'s port is published directly on `127.0.0.1`.
  Putting a reverse proxy in front requires setting `TRUST_PROXY` (see `.env.example`) so rate
  limiting keys on the real client IP, and terminating TLS there.
- **No automated backup/restore** (see above).
- **`jaeger` has no container healthcheck** (see "Start / stop" above); it is also not on the
  critical path -- `api`'s own `/health/ready` does not check it.
- **`app_user`'s password is not automated**: deliberately set via an interactive `psql`
  command rather than generated/stored by bootstrap SQL (see
  [security.md](security.md#local-login-setup)); `scripts/smoke.sh` scripts this step itself
  for disposable CI/smoke runs only, never for a real deployment.
